# Prompt Hub 公开首页与精选提示词库首发体验设计规格

日期：2026-05-21

关联 feature：`M1-001`

## 1. 背景

Prompt Hub 已完成基础工程骨架和 harness 治理，下一阶段需要进入第一个可供真实试用的公开业务切片。

当前使用场景以个人使用和分享给朋友为主，不以盈利或复杂运营为第一目标。因此首个业务切片应优先形成一个“能找到、能看懂、能复制”的内容闭环，并保留最小反馈信号帮助后续判断哪些提示词更有价值。

现有产品规格已经确认 v0.1 包含：

- 工具型首页。
- 20 条精选提示词库。
- 提示词详情和学习拆解。
- 公开统计中的浏览量和复制次数。

本规格将这些能力收束为 `M1-001`，让公开首页、提示词列表和学习详情在同一 feature 中形成首发体验。

## 2. 目标

`M1-001` 的目标是交付 Prompt Hub 第一个完整可用的公开内容体验：

- 首页保持工具型门户定位，并把用户清晰带向提示词库。
- `/prompts` 支持浏览首批 20 条精选提示词，并提供关键词搜索、分类筛选和标签筛选。
- `/prompts/[slug]` 提供可学习、可复用的提示词详情，包括正文、示例、结构拆解和优化对比。
- 用户可以复制提示词正文。
- 系统可以记录提示词详情浏览次数和复制次数。
- 内容由 seed 数据进入数据库，公开页面只呈现已发布内容。

## 3. 非目标

本 feature 不做以下事情：

- 不实现 `/generator` 的真实文本提示词生成。
- 不实现 `/image-to-prompt` 的真实上传、识图或视觉 provider 调用。
- 不实现 `/learn` 的完整教程正文。
- 不实现管理员 CRUD、发布流程或内容编辑界面。
- 不实现普通用户账号、收藏、评论、评分、付费、社区发布或复杂推荐。
- 不实现独立访客、趋势分析、埋点平台、反作弊系统或内容运营仪表盘。
- 不为了未来后台或 AI 工具提前新增本 feature 不需要的数据库结构和抽象层。

## 4. 方案选择

### 方案 A：完整公开内容切片

同一 feature 交付首页、列表、搜索筛选、详情学习页、20 条 seed 内容、复制与浏览计数。

优点：

- 首次交付即可给自己和朋友真实试用。
- 内容、学习拆解和复制行为形成闭环，反馈更接近产品价值本身。
- 与 v0.1 已确认的工具型门户和精选提示词库方向一致。

取舍：

- feature 面更宽，实施计划必须把内容、查询、页面和统计拆成独立可验证任务。

### 方案 B：页面能力先行

先交付首页、列表、详情和搜索筛选，只放少量示例内容，20 条内容另拆。

优点是工程验证更快。缺点是交付结果更像页面骨架，早期反馈会偏向界面而不是内容价值。

### 方案 C：提示词库优先

先交付内容、列表、详情和统计，首页只保留轻量入口。

优点是提示词库最快可用。缺点是首页和产品“工具型门户”的定位会暂时脱节。

### 决策

采用方案 A。`M1-001` 要交付可试用的公开内容闭环，但实施时必须坚持最小可验证任务拆分，不把这一 feature 扩展成后台、AI 工具或运营系统。

## 5. 信息架构

### 路由范围

本 feature 直接覆盖：

```text
/                  工具型门户首页
/prompts           精选提示词库列表
/prompts/[slug]    提示词详情和学习拆解
```

现有 `/generator`、`/image-to-prompt` 和 `/learn` 入口可以继续存在，但本 feature 不把这些页面升级为完整功能页。

### 页面关系

```text
首页
├── 精选分类入口 -> /prompts?category=...
├── 精选提示词入口 -> /prompts/[slug]
└── 提示词库主入口 -> /prompts

/prompts
├── 搜索与筛选 -> 过滤公开提示词
└── 提示词卡片 -> /prompts/[slug]

/prompts/[slug]
├── 复制提示词正文
├── 学习拆解内容
└── 相关提示词 -> /prompts/[slug]
```

## 6. 首页设计

首页采用“工具入口带内容承接”的方向：保留工具型门户姿态，同时把提示词库作为本 feature 中最完整的可用入口。

### 页面分区

1. 顶部导航与品牌入口。
2. 首屏价值主张，直说用户可以找提示词、看拆解、复制使用。
3. 三个核心入口：
   - 图片转提示词。
   - 文本提示词生成器。
   - 精选提示词库。
4. 精选分类入口，将用户带到带筛选参数的提示词库列表。
5. 精选提示词预览，展示少量已发布内容并进入详情。
6. 简短使用流程，说明找内容、读拆解、复制复用。
7. FAQ 和底部链接。

### 交互原则

- 首屏优先把真实入口和内容价值摆出来，不做纯营销横幅。
- 图片工具与文本生成器入口可以保留产品方向提示，但不能伪装成本 feature 已完成真实能力。
- 精选分类和精选提示词都应直接导向可用内容。
- 中文文案应简洁、明确，适合第一次分享给朋友时快速理解。

## 7. 提示词列表设计

`/prompts` 是寻找内容的效率页面。

### 页面分区

1. 页面标题和简短说明。
2. 关键词搜索输入。
3. 分类筛选。
4. 标签筛选。
5. 结果摘要，例如当前命中数量或筛选条件提示。
6. 提示词卡片列表。
7. 空态与无结果反馈。

### 列表卡片信息

每张提示词卡片至少应表达：

- 标题。
- 摘要。
- 分类。
- 标签。
- 提示词语言提示。
- 进入详情的明确动作。

### 搜索与筛选行为

- 搜索、分类和标签筛选通过查询参数表达，便于刷新、分享和回退。
- 列表只返回 `PUBLISHED` 提示词。
- 关键词搜索至少覆盖标题、摘要和提示词正文中对公开检索有价值的字段。
- 分类筛选和标签筛选必须能与关键词搜索共存。
- 默认排序保持简单稳定：精选内容优先，其后使用确定性顺序。
- 本 feature 不提供复杂排序控件、全文搜索引擎或语义检索。

### 状态设计

- 首批内容正常可用时展示 20 条精选提示词。
- 搜索无命中时，给出中文无结果反馈和清除筛选的回路。
- 若公开内容为空，页面应说明当前暂无可展示提示词，而不是呈现损坏布局。

## 8. 提示词详情设计

`/prompts/[slug]` 是学习和复用页面。

### 内容顺序

1. 标题、摘要、分类、标签和复制动作。
2. 提示词正文。
3. 示例输入与示例输出。
4. 结构拆解：
   - 角色。
   - 任务。
   - 上下文。
   - 约束。
   - 输出格式。
5. 普通版提示词与优化版提示词对比。
6. 优化说明。
7. 相关提示词。

### 交互原则

- 复制按钮围绕提示词正文提供，复制成功和失败都要有清晰反馈。
- 结构拆解要服务学习，不把主要正文挤成附属信息。
- 优化对比要帮助用户理解“为什么更好”，不只展示两段孤立文本。
- 相关提示词是继续浏览入口，不应盖过当前详情内容。

### 缺失内容处理

公开页面依赖经过 review 的 seed 内容。若单条公开提示词缺少本详情页要求的核心字段，应在数据验证阶段被拦住，而不是在页面上静默缺块。

## 9. 内容与数据设计

### 复用现有数据模型

本 feature 复用现有 Prisma 模型：

- `Prompt`
- `Category`
- `Tag`
- `PromptTag`

这些模型已经能支撑公开列表、筛选、详情、相关提示词、浏览次数和复制次数。

### Seed 内容

首批内容纳入本 feature，目标为 20 条已 review 的精选提示词。

内容分布沿用产品规格：

| 分类 | 数量 |
| --- | --- |
| 办公效率 | 4 |
| 学习成长 | 3 |
| 编程和 Agent 工作流 | 4 |
| 写作创作 | 3 |
| 营销和电商 | 3 |
| 图像和视频 | 3 |

每条 seed 内容必须能支撑详情页展示，包括：

- slug、标题、摘要、正文和语言。
- 分类与标签。
- 示例输入和示例输出。
- 结构拆解字段。
- 普通版提示词、优化版提示词和改进说明。
- 发布状态与精选标记所需信息。

### 公开读取规则

- 公开首页、列表和详情都只读取 `PUBLISHED` 内容。
- 未发布、归档或不存在的 slug 不应泄露正文。
- 详情不存在时使用明确的未找到行为。

## 10. 查询与相关内容

### 查询边界

公开查询层应为页面提供清晰职责：

- 首页精选内容查询。
- 列表搜索和筛选查询。
- 详情读取查询。
- 相关提示词查询。

查询层不应在页面组件内重复拼装复杂过滤规则。

### 相关提示词

相关提示词选择保持简单：

- 排除当前提示词。
- 优先同分类或共享标签。
- 返回少量固定上限内容。
- 不足时少显示，不为了填满引入复杂推荐逻辑。

## 11. 复制与浏览统计

### 浏览次数

- 用户访问有效公开详情时记录浏览次数。
- 未找到页不应增加浏览次数。
- 浏览计数是累计信号，不承担精准分析职责。

### 复制次数

- 用户触发复制提示词正文时记录复制次数。
- 复制反馈应先服务用户，计数失败不应阻断复制结果。
- 本 feature 只统计提示词正文复制，不扩展到示例、结构卡或任意文本块复制。

### 失败边界

- 计数失败应被隔离在统计路径中。
- 公开浏览、筛选、详情阅读和复制主流程不应因为计数写入失败而整体不可用。

## 12. 响应式与状态要求

- 首页、列表和详情都要在桌面端与移动端保持可读和可扫描。
- 筛选控件在窄屏下仍需清楚表达当前条件，不得遮挡列表。
- 长提示词正文、示例输出和优化对比都需要稳定换行和可复制阅读。
- 空态、无结果、复制反馈和未找到状态必须有中文反馈。
- 本 feature 的 UI 应复用项目现有导航和样式约束，再在页面级设计中补足内容层次。

## 13. 验证策略

### 内容与查询

- 验证 seed 加载能覆盖 20 条内容与分类分布。
- 验证公开查询只返回已发布内容。
- 验证关键词搜索、分类筛选和标签筛选能组合使用。
- 验证详情查询和相关提示词选择遵守公开范围。

### 统计

- 验证有效详情浏览会增加浏览次数。
- 验证复制行为会增加复制次数。
- 验证统计失败不会破坏公开阅读和复制主流程。

### 页面

- 验证首页包含提示词库主入口、精选分类和精选提示词预览。
- 验证列表页正常态、无结果态和公开内容为空态。
- 验证详情页正文、示例、结构拆解、优化对比和相关提示词区块。
- 验证不存在的 slug 走未找到行为。

### 浏览器检查

进入完成状态前至少记录：

- 首页桌面端和移动端入口检查。
- `/prompts` 搜索、分类筛选、标签筛选和无结果检查。
- `/prompts/[slug]` 详情阅读、复制反馈、长文本展示和相关提示词检查。
- 未找到页或等价错误反馈检查。

### 统一验证

最终必须运行：

```bash
npm run verify
```

## 14. 验收标准

`M1-001` 完成后应满足：

- 首页能够把公开用户引导到真实可用的提示词库体验。
- `/prompts` 能浏览首批 20 条公开提示词，并支持关键词搜索、分类筛选和标签筛选。
- `/prompts/[slug]` 能展示完整学习拆解内容，帮助用户理解并复用提示词。
- 公开页面不展示未发布或归档内容。
- 用户能复制提示词正文，并得到明确反馈。
- 有效详情浏览和正文复制能记录累计次数。
- 统计失败不会阻塞阅读或复制主流程。
- 相关提示词保持简单、可理解且不越出公开内容范围。
- 对应专项验证、浏览器检查和 `npm run verify` 均有新鲜证据。

## 15. 后续拆分

完成 `M1-001` 后，后续 feature 可按价值继续拆分：

- 文本提示词生成器真实流程。
- 图片转提示词真实上传和视觉分析流程。
- `/learn` 教程内容。
- 管理员内容维护与发布流程。
- 更细的内容运营与质量反馈能力。
